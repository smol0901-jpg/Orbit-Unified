# Подготовка к базе данных (версия 5.8)

Цель: к 5.8 данные приложения должны быть готовы к переезду в БД, а переезд — быть заменой одного слоя, а не переписыванием. Сейчас **всё хранится локально**, облако законсервировано (`docs/CLOUD-STUBS.md`).

## 1. Что хранится сейчас (инвентаризация)

| Где | Ключ / имя | Содержимое | В БД? |
|---|---|---|---|
| localStorage | `orbit-planner-v3` | главное состояние: `profile`, `lessons` (встречи), `clubs` (блоки), `buses` (маршруты), `notes`, `homework` (задачи), `goals`, `people` (контакты), `holidays` (отпуск), `dayLogs` (журнал), `events`, `reminders`, `packChecks`, `settings` | да |
| localStorage | `orbit-planner-backup-v3` | копия предыдущего состояния | нет (локальная страховка) |
| localStorage | `orbit-memory-v5` (старое `v4`) | память агента: `aliases`, `notes`, `msgs` (до 300), `facts`, `favCall` | да |
| localStorage | `orbit-scripts-v1` | сценарии пользователя | да |
| localStorage | `orbit-habits-v1` | привычки | да |
| localStorage | `orbit-cron-v1` | локальные расписания (`cron.js`) | да (`script_jobs`) |
| localStorage | `orbit-action-log-v1`, `orbit-snapshots-v1`, `orbit-notified-v1`, `orbit-welcome-v4` | служебное: журнал действий, снимки, «уже уведомлял», приветствие | нет (или по желанию) |
| IndexedDB | `orbit-agent-v1` → хранилище `knowledge` (`phrase`, `meaning`, `ts`) | чему агент научился («слово = значение») | да |
| CIFRA | IndexedDB `raschet` → `h` (история вычислений), `cfg` в localStorage | история и настройки калькулятора | по желанию |
| FlowForge | `flowforge-backup` | схемы | по желанию |

Что важно в текущем формате:
- у записей есть `id` вида `uid()` = `Date.now().toString(36) + случайные символы` — это **не UUID**, поэтому в БД `id` записей — `text`;
- нет `schemaVersion` у данных, нет `createdAt` / `updatedAt` / признака удаления;
- `migrate()` в `js/app.js` достраивает недостающие поля при каждой загрузке — это хорошая основа для версионных миграций.

## 2. Что подготовить в коде до 5.8 (чек-лист)

- [ ] **Слой данных `Orbit.store`.** Единые `get / add / update / remove / list` по типам записей; остальной код перестаёт трогать `state.lessons` напрямую.
- [ ] **`schemaVersion`** в корне состояния и **журнал миграций** (`migrate()` → цепочка `v1→v2→…`, каждый шаг проверяется тестом).
- [ ] **`createdAt` / `updatedAt`** (ISO-время) у каждой записи; обновляются слоем данных автоматически.
- [ ] **Удаление «с надгробием»:** вместо физического удаления — `deletedAt`; физическая очистка по расписанию. Иначе синхронизация воскресит удалённое.
- [ ] **Идентификаторы:** оставить `uid()`, но гарантировать уникальность (добавить случайную часть длиннее) либо перейти на `crypto.randomUUID()` для новых записей.
- [ ] **Очередь изменений (outbox)** локально: каждое изменение записывается в журнал `{kind, id, op, at}` — сервер потом просто «проигрывает» его.
- [ ] **Экспорт / импорт** целиком (JSON) с проверкой версии схемы и тестом «экспорт → очистка → импорт → то же самое».
- [ ] **Резервная копия перед миграцией** (уже есть `backup-v3` — расширить до нескольких версий) и кнопка «откатить».
- [ ] **Настройки приватности:** что синхронизируется (напр. переписка с Коном — отдельный переключатель, `cloudAgentWall` — запрет писать на стену).
- [ ] **Тесты:** миграции старых данных (пример — `templates/schema-example.json`), повреждённые данные, большие объёмы.

## 3. Целевая схема

Файлы в `db/migrations/`:

- `001_init.sql` — таблицы облака из `cloud.js`: `profiles`, `profile_private`, `chat_messages`, `wall_posts`, `friendships`, `messages`, `script_jobs`, журнал `schema_migrations`, правила доступа (RLS), триггер создания профиля, очистка переписки до 100 МБ.
- `002_records_sync.sql` — синхронизация данных по записям: `records` (одна таблица для всех типов записей) и `documents` (настройки, память агента и т. п.).

### Соответствие «локально → облако»

| Локально | Облако |
|---|---|
| `lessons`, `clubs`, `buses`, `notes`, `homework`, `goals`, `people`, `holidays`, `dayLogs`, `events`, `reminders` | `records` (`kind` = `lesson`, `club`, `bus`, `note`, `homework`, `goal`, `person`, `holiday`, `daylog`, `event`, `reminder`) |
| `settings`, `profile`, `packChecks` | `documents` (`name` = `settings`, `profile`, `packChecks`) |
| `orbit-memory-v5` (`aliases`, `facts`, `notes`, `favCall`) | `documents` (`name` = `agent-memory`); `msgs` → `chat_messages` |
| `orbit-scripts-v1`, `orbit-habits-v1` | `records` (`script`, `habit`) |
| `orbit-cron-v1` | `script_jobs` |
| IndexedDB `knowledge` | `records` (`kind` = `knowledge`, `id` = фраза) |

## 4. Синхронизация и конфликты
- **Единица синхронизации — запись.** Побеждает изменение с более поздним `updated_at` (last-write-wins); для настроек и памяти агента — слияние по полям.
- **Удаление** — запись с `deleted_at`; клиент при получении убирает её локально.
- **Первая синхронизация** нового устройства: сначала загрузка с сервера, потом отправка локальных отличий; при расхождении — спрашивать пользователя (оставить локальное / серверное / объединить).
- **Нет сети:** действия копятся в outbox и уходят при появлении связи; приложение работает как раньше.

## 5. Безопасность
- В приложении только публичный `anon`-ключ. Ключ `service_role` — только в Edge Functions.
- Все таблицы с включённым RLS (политики в SQL). Проверка: два тестовых пользователя не должны видеть данные друг друга (кроме разрешённого: имя и «был в сети» у друзей, стена).
- Пароли — только через Supabase Auth; e-mail подтверждается. Приватные данные (`state`, `push_sub`) лежат отдельно от публичного профиля.
- Нужны: удаление аккаунта со всеми данными, экспорт данных пользователя.

## 6. План переезда данных пользователя (в 5.8)
1. Резервная копия локальных данных (автоматически, перед первым включением облака).
2. Вход в аккаунт → выбор: «загрузить мои данные в облако» или «взять данные из облака».
3. Загрузка пакетами (по 200 записей) в `records`/`documents`, проверка количества, отметка в `schema_migrations`/профиле.
4. Включение режима синхронизации. Откат: кнопка «отключить облако» — локальные данные остаются нетронутыми.

## 7. Риски и вопросы к решению
- Supabase может не открываться без VPN в некоторых сетях → режим «без облака» остаётся основным; решить, нужен ли запасной вариант (свой сервер).
- Объём переписки (до 100 МБ на пользователя) и стоимость хранения.
- Модерация стены и личных сообщений; возраст/согласие; политика хранения данных.
- Что делать с историей калькулятора и схемами FlowForge — синхронизировать или нет.
